# 第 4、5 题共用讲解与故障推演

先读[第 4 题主答](architecture-q4.md)和[第 5 题补充](architecture-q5.md)，再用这份材料展开原因和故障场景。两题的方案属于设计推演，不代表实际做过订单项目。当前代码只有三个只读工具和会话管理，下面的订单、任务执行记录、租约与事件机制均是设计方案。

## 一次购买，为什么会留下几种不同的记录

假设用户确认“买一件商品 A”。应用给这次操作分配 `op_001`，订单服务随后创建 `order_100`，但响应在网络中丢失。

| 记录 | 此时可能是什么 | 它说明什么 |
| --- | --- | --- |
| 模型工具调用 | `tool_call_id = call_a` | 本次结果要配回哪条模型消息 |
| Agent 任务记录 | `op_001`，原命令，等待查证结果 | Agent 接下来应该做什么 |
| 后端操作记录 | `op_001` 已成功，结果指向 `order_100` | 同一命令重复到达时怎样处理 |
| 后端订单 | `order_100` 已创建，待付款 | 业务实际上处于什么状态 |
| 对话记录 | “请求超时，暂时无法确认” | 当时向用户解释过什么 |

这些记录的职责不同。Agent 的“等待确认”和后端的“已经成功”可以暂时同时存在；恢复流程查回结果后再推进任务。订单状态以后还可能变化，所以重放当初的创建结果，也不能代替查询订单现在是否付款。

第 4 题要回答：再次发送 `op_001` 时，怎样只得到原来的 `order_100`？第 5 题要回答：各处看到的状态不同时，谁能裁决业务事实，Agent 怎样继续工作？

## 第 4 题：把关键判断讲明白

### 为什么模型调用 ID 不能直接防止重复下单

模型重试后可能生成 `call_b`，参数也可能换一种表达。工具调用 ID 是协议上的配对标识，不能替业务决定“这是不是另一笔购买”。

应用要把操作 ID 绑定到一个已经接受的业务意图，并保存确认后的命令。恢复时读取原记录。若用户明确要再买一份，建立新操作；若用户只是催问，就查原操作。无法判断时澄清，不能只比较两句话是否相似。

参数哈希也不能单独充当操作身份。同样的商品和数量可以对应两次合法购买；哈希适合检查同一个 `operation_id` 的命令是否被改动。

### 同键同参，怎样判断“参数相同”

先做格式校验，按固定规则补全默认值、统一字段表示，再对影响业务的字段计算摘要。字段顺序不同的 JSON 应视为相同；商品、数量、收货信息或确认的报价不同，应视为不同命令。请求时间、重试次数和临时凭据不应进入摘要。命令结构发生升级时，也需要明确版本和兼容规则。

每次请求都要检查身份和访问权限。对于已完成且同键同参的操作，返回原结果；库存、价格和可售状态等可能变化的业务检查，应属于首次业务执行的事务，而不能在重放原成功结果之前重新下单检查一遍。否则，第一次买走最后一件商品后，重试反而可能收到“库存不足”。

### 唯一约束和事务各解决什么

两个请求可能同时查询，都看到“没有记录”。数据库唯一约束保证它们不能都成功占用同一个操作键；事务保证业务效果和执行结果一起提交。

在同库方案中，操作键插入、必要业务写入和成功结果保存处于一个事务。提交前进程退出，整个事务回滚；提交后响应丢失，重试读取已提交结果。若客户端连数据库提交是否成功都不知道，就重新按操作键查询，而不是凭异常类型认定失败。

不要把外部 HTTP 调用包在本地数据库事务里，就认为获得了同样的原子性。远端可能已经提交订单，本地事务却回滚；这正是需要下游幂等键和结果查询的原因。

### UNKNOWN 和“允许重试”为什么并不矛盾

`UNKNOWN` 表示调用方目前不知道业务结果。重试是否安全则取决于下游契约，这是两个判断。

| 已知情况 | 可以怎样做 |
| --- | --- |
| 查到原操作已成功 | 保存结果，返回原订单 |
| 查到确定性业务拒绝 | 保存该操作的失败结果 |
| 未知，但原键仍受下游幂等保障 | 在预算内重发原键和原命令，继续核对结果 |
| 未知，且没有可确认有效的幂等保障 | 停止自动重发，保留待确认并对账 |

因此，不能写成“只有证明未执行才可同键重试”；也不能写成“超时都可以重试”。查询接口暂时查不到可能是同步延迟，过期的处理中记录也可能是旧 worker 仍在执行。都需要按契约恢复，不能自行换键。

### Runtime 的策略声明是不是保证本身

开发者注册工具时，可以声明 `read_only`、`keyed` 或 `none`，配置操作键来源、查证方式、重试错误和预算。Runtime 验证条件并调度；工具背后的服务负责兑现保证。

只写一个 `idempotent=true` 不会自动产生唯一约束、事务或远端去重。新增工具时应核对其实现、有效期和测试结果。默认未知的写工具应按没有自动重试保障处理。

只读查询重复执行可能得到不同内容，因为数据在变化。这里关心的是是否重复产生订单等业务效果；如果任务还要求多次查询看到同一时点的数据，需要另行设计读取快照。

### 重试的次数、时间和错误怎样选

次数和时间由业务等待预算、下游延迟及限流情况决定，没有所有工具通用的最佳值。比如“最多 3 次”应说明包含首次尝试，同时限制总时长和单次超时。下一次等待或请求已放不进剩余预算，就结束本次尝试。

固定参数错误、权限错误和同键异参不应原样重试。429、部分 5xx、网络故障仅是候选原因；仍须满足幂等条件。使用有上限的指数退避和随机抖动，在预算允许时遵守 `Retry-After`，并避免 SDK 与 Runtime 各自重试导致次数相乘。[AWS 的重试说明](https://aws.amazon.com/cn/builders-library/timeouts-retries-and-backoff-with-jitter/)

若只是模型请求失败、还未发出业务命令，可以按模型接口策略决定重试。一旦命令已发出，恢复应读取保存的命令及结果，不让一次新的模型规划无意中创建第二笔订单。

## 第 4 题进阶：过期和并发接管

### 幂等记录不能无限保存，怎么清理

TTL 是记录保留多久的规则，应覆盖最大重试、恢复和回调窗口。它到期只能说明缓存可以按策略处理，不能证明一个未知订单从未执行。

成功订单应保留来源操作唯一键和必要的命令摘要，使缓存清理后仍能找到原订单并拒绝异参复用。操作失败、订单已归档等情况同样要定义保证范围：若不永久保留完整去重记录，就必须约定可接受的重放期限，并拒绝过期操作被当成新操作接受。要做到这一点，仍需保留最小过期记录或可验证的操作期限，不能删掉记录后凭空识别旧请求。未解决的 `UNKNOWN` 不能随普通缓存直接删除。

外部服务有自己的保留窗口。该窗口已过、结果仍未知时，继续对账；不能假设换键或重用旧键仍能防重。Stripe 对键清理和参数比较有明确规定，可用来理解“幂等性有契约范围”，不能直接套用到其他供应商。[Stripe 幂等请求说明](https://docs.stripe.com/api/idempotent_requests)

### 一个 Redis 锁够不够

锁可以减少多个 worker 同时干活。租约则是有时限的锁：持有者很久没续期，别人可以接管。但旧 worker 可能只是暂停，租约过期后仍会继续执行。

fencing token 可以理解为递增的接管编号。新的持有者得到更大编号，受保护资源在写入时检查编号，拒绝旧持有者的写入；检查和写入必须正确地组成原子操作。

它的保护范围取决于谁检查这个编号。如果远端订单 API 不支持检查，本地 fencing 无法阻止旧 worker 向远端发请求。因此，租约用于协调工作，业务唯一约束或下游幂等键用于控制重复效果。基础的同库下单方案不必先引入 Redis 和租约。

## 第 5 题：让业务事实和任务进度各有归属

### Agent 能不能存订单数据

可以保存业务引用和必要快照，例如订单 ID、上次看到的状态、版本及查询时间。关键是明确它的来源和用途：用来展示旧结果、辅助推理或减少查询，不允许它与后端分别接受独立的订单状态写入。

这是一种逻辑分工，不要求必须建立多个物理数据库。初版完全可以在同一数据库里分表，业务表由受控业务接口修改，任务表由执行管理模块推进。物理部署方式不会自动解决归属问题；两处都认为自己能决定订单是否付款，放在同一个库也会冲突。

### Agent 的任务状态需要保存到什么程度

恢复副作用操作至少要知道：正在完成什么任务、哪个已确认步骤尚待结果、固定 `operation_id` 是什么、原命令是什么、已收到哪些权威结果及业务引用。应在关键调用前保存命令，在结果确认后保存任务推进。

聊天摘要可能截断、过期或遗漏信息，不能承担这项职责。当前项目是在一轮结束时保存对话，这对三个只读工具足够；如果扩展成下单工具，需要新增上述执行记录，不能直接把现有会话 SQLite 当作已经完成的订单恢复机制。

### 为什么还保留后端业务校验

Agent 可以承担大部分流程编排，例如选哪个商品、何时询问用户、下一步调用哪个工具。权限、余额、库存和订单状态约束必须在业务提交处确定地检查，才能对来自不同客户端的操作一视同仁。

这不是要求 Agent 和后端重复实现两套业务规则。Agent 可以提前检查以改善交互，但提交处的校验才决定是否允许写入。若将来由 Agent 服务负责某个业务领域，也应由其中受控的业务模块和持久化记录裁决，不能让模型上下文成为唯一事实来源。

### 两个版本号为什么不能混用

| 版本 | 保护什么 | 不能推导出什么 |
| --- | --- | --- |
| 会话 `revision` | 防止旧会话覆盖同一会话的新历史 | 无法知道订单是否被手机端修改 |
| 业务 `order_version` | 防止基于旧订单版本提交冲突修改 | 无法说明 Agent 的对话或任务进度是否已保存 |

用户在手机上付款后，订单可能从版本 1 变成版本 2，而当前会话一条新消息也没有。Agent 提交带旧 `expected_version` 的更新，业务服务应原子检查并返回冲突。Agent 查询新状态后重新评估，而不是覆盖它。

权威查询也需要约定读取的一致性；不能从一个可能滞后的副本查不到，就判断业务不存在。关键变更仍在后端事务内核对当前事实，避免“刚查完就被另一请求改了”的竞争。

### 后端没响应，怎样向用户说清楚

“订单请求已发出，目前还没确认结果”对应待确认步骤。“上次查询时是待付款，查询时间是……”对应一份有时点的快照。只有取得可信结果，才更新已确认的任务步骤和业务展示。

恢复查询或接收到通知后可以修正 Agent 的观察，但不应为了让两边看起来一致，反过来把后端已经成功的订单改成失败。撤销或退款是另一个有业务含义的操作，需要独立规则。

## 第 5 题进阶：什么时候需要事件和 outbox

如果很多任务都在等待订单状态变化，持续轮询可能浪费资源，可以由后端发布事件，让 Agent 刷新快照或唤醒待处理任务。缓存与业务库之间可能暂时不同步，所以事件通知仍需配合恢复查询。[Microsoft 对缓存一致性的说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside#problems-and-considerations)

订单更新成功后，发送事件可能失败。事务 outbox 的做法是在同一个数据库事务里同时写订单和“待发送事件”记录，再由后台程序发送。发送成功后的确认也可能丢失，因此消费者仍要处理重复事件；这不是全链路只处理一次的保证。[AWS：Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

消费端可以用事件 ID 去重，并把去重记录和本地状态更新放在同一个事务。携带完整订单快照的事件，可按订单版本防止旧快照覆盖新快照；若事件只是增量，不能简单跳过缺失版本，应补齐或重新查询权威记录。后续触发的新业务操作仍要有自己的稳定操作 ID。

这些机制适合需求增长后再引入。当前两题的基础方案先把数据归属、查询恢复和幂等命令讲清楚，不要求先上消息队列、事件溯源或分布式事务。

## 故障推演与将来的测试清单

下面是订单设计需要验证的情况，当前项目没有执行这些订单测试。推演时同时记下“订单数量”“业务状态”“Agent 知道什么”，避免只看最终回答。

| 情况 | 期望结果 |
| --- | --- |
| 同键同参顺序重试、并发重试 | 只创建一笔订单，重复请求最终取得同一订单引用 |
| 同键异参 | 返回冲突，不创建或覆盖订单 |
| 相同参数，但用户明确发起两次购买 | 两个独立操作各创建一单 |
| 同库事务提交前崩溃 | 操作与订单一起回滚；安全恢复时仍使用原操作身份 |
| 提交成功，返回结果前连接断开 | Agent 保持待确认，查询或同键重放取得原单 |
| 外部已创建订单，但查询尚不可见 | 不据此换键；按有效幂等契约重试或继续对账 |
| 处理中租约过期，旧 worker 随后恢复 | 旧本地写入被 fencing 拒绝；远端效果由远端幂等契约保护 |
| 成功结果缓存过期 | 根据持久化业务键及摘要找回，或按契约拒绝过期重放 |
| 外部幂等窗口已过，业务结果未知 | 停止自动重发，继续查证 |
| 持续 429、5xx 或超时 | 尝试次数和总预算有界，未知结果不伪装成确定失败 |
| 后端已成功，Agent 保存进度前退出 | 从原任务记录恢复，按操作 ID 查回后推进任务 |
| 其他端更新订单，Agent 持有旧版本 | 旧版本修改被拒绝，重新查询后评估 |
| 对话摘要被截断或整个会话被清理 | 已确认业务事实不丢失；任务恢复依赖独立执行记录 |
| 后端不可用 | 只展示有时点的旧快照或待确认状态，不编造当前成功结果 |
| 事件重复、乱序或暂时没送达 | 不重复推进业务；不被旧快照覆盖；可通过补齐或查询恢复 |

查错时记录操作 ID、模型调用 ID、订单引用、尝试序号、状态变化、版本和错误类别即可形成关联。应避免把密钥和完整订单隐私写进普通日志；重点关注待确认任务积压、冲突次数及恢复耗时。

## 两段简要回答

第 4 题的简要版本：

> 下单超时可能是订单已经成功、响应没回来。调用前先保存稳定的操作 ID 和命令，服务端用唯一约束与事务去重。同键同参拿原结果，异参报冲突。Runtime 依据开发者注册的工具策略决定是否重试。外部结果未知时先查证，只有有效幂等契约下才同键重发，否则继续对账。次数和时间预算控制请求量，业务服务负责控制重复效果。

第 5 题可以接着讲：

> 订单是否付款由业务服务裁决；Agent 保存自己正在做什么、对应哪个操作和订单。它能保存带版本与时间的快照，但关键操作仍回到业务接口。后端成功、Agent 没收到时，按操作 ID 查回；其他客户端修改过订单时，用业务版本检测冲突。任务恢复信息独立保存，对话摘要丢失不会改变业务事实。

关于当前实现：Runtime 提供只读工具调用、会话隔离、有限上下文和恢复等能力；订单幂等、业务版本、独立任务执行记录和事件机制属于架构答案中的设计，尚未实现。

## 设计要点

- 区分模型调用 ID、业务操作 ID 和订单 ID，并解释合法的重复购买。
- 同库事务在提交前、提交后崩溃时分别留下哪些记录。
- UNKNOWN 状态下，哪些同键重试安全，哪些必须停止。
- 租约、唯一约束、事务各自保护的范围。
- 业务事实、任务步骤和聊天摘要的区别，以及两种版本号。
- “手机已付款，但 Agent 仍记得待付款”应如何处理。
- outbox 解决什么问题，以及为什么仍需消费去重。

# AI Prompt 与问题解决记录

这份记录按时间写，主要记三件事：我让 AI 做了什么、哪些地方我没照它说的做、最后怎么验证。代码初稿是 Codex 打的，范围、取舍和验收是我定的。具体的 prompt 我单独放在 [prompts.md](prompts.md)，这里更多写过程和踩过的坑。

## 一开始定下的几条

**不用现成的 Agent 框架。** 题目要求核心 Runtime 自己实现，我也得能在面试里指出每一步在哪。LangGraph 这类框架会把 loop 藏进图里，出问题不好定位，所以一开始就没考虑。

**三个工具都做只读的。** calculator、search、read_docs。search 用本地 JSON 语料，不接真实搜索：题目允许 mock，真实搜索会带网络、key、限流，测试和证据都会变复杂。read_docs 只认三个固定 ID，不让模型传路径。

**会话用 SQLite，不引入 Redis。** 这是单机 CLI，SQLite 够用，还能演示重启恢复。并发我只做到“同一 Runtime 同一会话拒绝并发 + 保存时 revision CAS”，没把它说成分布式锁。后来准备第 4 题时，这一点反而成了很好的反面例子：会话 revision 防不了重复下单。

**压缩按完整轮次。** 一开始也想过只删旧消息，但那样可能留下 tool 结果却丢了 tool_call，下一次请求协议就不完整。所以按一整轮删，旧轮次压成摘要。摘要会丢信息，这个我认。

**HTTP 不自动重试。** 超时只说明没收到结果，不能证明远端没执行。读接口重试问题不大，写接口重试可能重复下单。这个判断后来直接变成第 4 题的核心。

**Responses 的推理上下文保留，但不展示。** 工具往返需要把 encrypted_content 原样带回去，否则模型会丢状态；但我不解密、不打印、不写日志。Messages 那边的 thinking 我直接报错，不假装支持。

## 10 月 8 日：先跑起来

第一天基本是在搭骨架和踩环境问题。

| 问题 | 处理 |
|---|---|
| 网页工具读不了飞书 | 换浏览器直接读原题，把要求逐条抄到 `docs/requirements.md` |
| unittest 清理临时数据库时报了 14 个错 | SQLite 的上下文管理器只负责事务，不负责 close；补了显式关闭 |
| 日志路径不可写时 `ask` 直接抛异常 | `Trace` 捕获写入失败，提示一次后继续；补了回归 |
| 跨轮重复的 tool_call_id 污染历史 | 从已保存历史收集 ID，执行前拒绝重复 |
| 测试用例互相影响 | 不同子用例共用了 session 和 ID；改成独立会话 |
| 旧模型第一次真实请求就失败 | 单次诊断是 HTTP 502，上游拒绝；留了记录，没重试 |

后来换了新的模型接入。第一次截图 OCR 把 key 读错了，返回 401；改用隐藏输入重新录入，key 只以 DPAPI 密文保存。接着按官方文档补 Responses 适配，测试从 54 加到 55（reasoning item 的 status 可以是 null）。第一次正确凭据的验收里，三个工具的汇总超过 40 秒超时；把单次超时显式调到 90 秒后重跑，6 个场景全过，8 次 HTTP 请求，没有自动重试。那天所有阶段加起来是 15 次生成请求尝试，包含失败、401 和超时，不是 15 次成功。

## 10 月 9 日：自己挑毛病

第二天的主要工作不是加功能，是审查。先把原题重新对了一遍，再跑原有 55 项测试，然后并行看协议、Runtime 和文档。下面这些是当时挑出来的：

| 问题 | 处理 |
|---|---|
| 只有 commentary 的响应被判完成 | 新响应解析返回 `model_incomplete`；普通无 phase 回答和历史回放保留 |
| 旧 Messages 丢掉 thinking 后继续 | 明确返回 `model_unsupported_thinking`，把兼容范围写进文档 |
| 摘要原始长度合格，转义后总上下文仍超限 | 完整轮次压缩后，继续按实际序列化大小淘汰摘要 |
| SQLite 启动或列表查询故障直接抛异常 | 增加受控提示；损坏数据库不自动重建 |
| 空 `--ask` 误入交互模式 | 区分“没传参数”和“传了空字符串”，空输入由 Runtime 拒绝 |
| 旧协议、旧状态和新说明混在一起 | 跟读改为 Responses 主线，按阶段整理工作记录 |
| 第 4 题 UNKNOWN 的重试条件前后不一致 | 统一成“先查询，有效幂等契约下才同键重发，否则待确认” |
| 还没有第 5 题材料 | 补业务事实、任务进度、会话记忆的归属和恢复场景 |

修完是 64 项测试。用同一套平台配置又跑了一次有界验收：6 个场景、8 次请求、0 重试；新记录单独存，没覆盖前一天的。干净包复现也做了：重新建 venv、装依赖、跑测试、跑 CLI、切会话、退出再启动，全部通过。

到这一步，真实请求累计记录是 23 次生成尝试，包含认证失败、上游拒绝和超时；不是 23 次成功，也不代表未来每次都能成功。

## 几条我考虑过但没做的路

- **加 FastAPI、前端、向量库**：题目没要求，而且会让“运行方式”和“证据”变复杂。命令行足够把 loop、工具、会话讲清楚。
- **search 接真实网络**：mock 更可控，测试不会因为网络抖动变得不可复现。
- **用 Redis 做会话锁**：单机 CLI 用不上；SQLite CAS 已经能说明并发边界，再引入 Redis 反而要多解释一层。
- **把 thinking 明文打印出来**：不安全，也不是可靠事实；我选择保留协议上下文、明确拒绝不支持的块。
- **把失败轮次也存进历史**：早期为了保留完整工具配对，我把程序生成的失败提示也保存成 assistant 消息。提交前复核发现它会混进下一轮上下文；现在改为只有模型给出最终答案后才保存整轮。当前工具全是只读的，失败轮次的工具请求和结果也一起丢弃，并用回归测试确认旧历史不受影响。

## 还没完全讲顺的地方

有几处我能跑通、但讲起来还不够顺，记在这里，后面一项项补：

- 一次工具往返的消息顺序，要能不看代码画出来；
- 改一个 Schema 之后，哪一步会失败、错误怎么回到模型；
- 摘要具体丢了什么，为什么字符预算不等于 token；
- 下单超时后，哪些记录已经存在、哪些还不知道；
- 第 5 题里，为什么不能拿聊天历史判断订单当前状态。

这些是我接下来要补的，不是“已经掌握”。

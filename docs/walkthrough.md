# 顺着一次计算和追问，读懂这份 Agent

先运行 README 里的离线例子，再读这篇。目标是能在代码中指出：谁决定调用工具、谁真的执行、结果怎样回到模型，以及下一次提问为什么能接着聊。

下面用“计算 (17+25)*3，再把结果加 8”串起整个过程。消息内容和调用 ID 是教学示例；实际请求结果见[验证记录](../verification/README.md)。

## 1. 从命令行进入主循环

`python -m agent` 会运行 `agent/__main__.py` 的 `main()`。它先选择模型，再创建工具注册表、会话数据库、记忆策略和日志器，最后把这些对象交给 `Runtime`。把组件传进去，使测试可以替换模型，而不必另写一套主循环。

真实模式默认从环境变量读取配置；也可以用 `--config-dir .local/private` 明确加载本机加密配置。默认协议是 Responses。`--demo` 则选择 `DemoModel`，只根据固定前缀触发工具，不调用网络，也不会理解任意自然语言。

用户输入后，CLI 调用：

```python
runtime.ask(user_id="local-user", session_id="window-1", text="请计算 (17+25)*3。")
```

`ask()` 检查输入长度和会话是否正在运行，再交给 `_run()`。同一个 Runtime 实例内，同一会话同时只能进行一轮；这样两条请求不会交叉追加到一份历史。两个独立进程还可能同时执行，后面的保存版本检查负责防止互相覆盖。

想先看结果，可运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m agent --demo --data-dir .local/walkthrough --session calc --ask "计算 (17+25)*3"
```

这次会得到 126，通常调用模型接口两次、计算器一次。离线模式里的“模型接口调用”只是调用 Python 方法，不代表两次 HTTP 请求。

## 2. 第一次问模型：做决定，还没有执行工具

`Runtime._run()` 按 `(user_id, session_id)` 读取这次会话，然后向模型发送历史、当前问题和工具说明。工具说明包含名称、用途和参数格式，模型根据这些信息提出调用。

`agent/models.py` 定义了统一返回格式。例如：

```python
ModelReply(
    content="我先算一下。",
    tool_calls=[ToolCall("call_1", "calculator", '{"expression":"(17+25)*3"}')],
)
```

这里的 `ToolCall` 是请求，不是计算结果。`arguments` 是 JSON 字符串，程序还没有相信它的内容。

`ModelReply` 还有一个 `provider_items` 字段，用于保存 Responses 续接时需要的原生输出，例如 phase 和不透明加密上下文。它随所属消息保存和回传；程序不解密，不把这些内容写进 trace。你阅读核心循环时，先理解 `content` 和 `tool_calls`，再回头看适配器如何保存这个字段即可。

`Model` 使用 Python 的 `Protocol` 约定一个 `complete(messages, tools)` 方法。真实模型和模拟模型都实现它，所以 Runtime 不需要知道当前接的是哪家接口。`Protocol` 不是参数安全检查，运行时仍需校验实际返回内容。

## 3. 注册表找到计算器，验证参数后执行

看 `agent/tools.py` 的 `ToolRegistry.schemas()` 和 `execute()`。注册工具时，程序同时保存名称、说明、JSON Schema 和处理函数。Schema 就是参数的格式约定，例如计算器必须收到字符串形式的 `expression`，不能多带任意字段。

执行分成几个很具体的动作：按名称找工具；把参数字符串解析为 JSON；检查参数是否符合 Schema；调用处理函数；把结果整理成统一格式。模型给了不存在的工具、错类型或多余参数时，执行会被拒绝。

计算器也没有直接 `eval()` 模型给出的字符串。它先用 Python 的 `ast` 模块把表达式拆成语法树，只接受数字和允许的运算节点，并限制表达式长度、节点数、数值和指数范围。这样 `(17+25)*3` 可以计算，函数调用、变量名或属性访问则会被拒绝。

成功结果大致如下：

```json
{"ok":true,"data":{"expression":"(17+25)*3","value":126}}
```

工具出错时使用相同的外层结构：

```json
{"ok":false,"error":{"code":"invalid_arguments","message":"工具参数不符合 Schema。"}}
```

这是结构示意，具体错误文案以代码为准。模型能看到错误并修正参数，但不能绕过注册表。search 读取本地小语料；read_docs 只接受 runtime、session、memory 三个文档 ID，不接收任意文件路径。

## 4. 第二次问模型：它现在看到了计算结果

Runtime 先追加 assistant 的工具请求，再追加对应的 tool 结果，两者使用同一个调用 ID。核心历史可以简化为：

```text
user：请计算 (17+25)*3。
assistant：调用 calculator，ID=call_1，expression=(17+25)*3
tool：ID=call_1，结果 126
assistant：结果是 126。
```

最后一条由第二次模型调用产生。工具负责计算，模型负责结合问题解释结果。如果模型认为还需要其他工具，循环可以继续；没有工具且回复完整时结束。默认每轮最多调用模型 6 次，每次最多提出 4 个工具调用。

协议适配发生在 `agent/responses_provider.py`，HTTP 发送复用 `provider.py`：

| 内部内容 | Responses 请求或输出 |
|---|---|
| system 规则 | `instructions` |
| assistant 工具调用 | `function_call`，包含 `call_id`、工具名和参数 |
| tool 执行结果 | `function_call_output`，使用相同 `call_id` |
| 工具 Schema | function 工具的名称、描述与 `parameters` |
| 原生 assistant 输出 | 随 `provider_items` 保留，并在回放前核对内容和工具配对 |

`_payload()` 负责转换请求，`complete()` 发送一次 HTTP 请求，`_parse()` 检查返回并形成 `ModelReply`。HTTP 200 只代表收到响应，还要检查协议和完成状态。尤其 `phase=commentary` 只是“我正在处理”之类的进展；如果只有这类文本、没有工具调用，程序会返回 `model_incomplete`，不能把它当成任务已完成。普通没有 phase 的回答仍可使用。

旧的 Messages 协议用 `tool_use/tool_result` 表达工具往返，作为显式兼容选项保留。当前适配器不支持 thinking 或 redacted_thinking 块，遇到会明确报错；相关模式不能靠丢弃字段后继续请求来兼容。

## 5. 追问为什么能得到 134

完成第一轮后，SQLite 保存的是整个消息组。用户再问“把刚才的计算结果加 8”，Runtime 重新读取同一会话，把前一轮结果和新问题一起发送给模型。

模型可以据此提出 `126+8` 的计算请求。调用 ID 可以变成 `call_2`，因为这是新一次工具调用；结果仍按同一个 ID 配回。保存历史的是程序，根据历史理解“刚才”指什么的是模型。

可以用真实模式观察这个过程：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m agent --config-dir .local/private --data-dir .local/walkthrough-real --session calc
```

依次输入“请计算 (17+25)*3”和“把刚才的结果再加8，请用计算器确认”。离线模拟不支持第二句的语言理解；用它测试时，应输入完整的“计算 126+8”。

同一用户切换到 `window-2` 时，数据库查询键变了，新窗口不会收到上述 `calc` 会话的历史。用 `/switch calc` 切回后又会读到原记录。不同用户即使使用相同 session 名，也属于不同的键。`--user` 是本地演示参数；线上身份应来自鉴权，而不能直接相信用户提交的字符串。

## 6. 聊得越来越长时，程序保留什么

看 `agent/memory.py` 的 `MemoryPolicy`。这里有两种不同上限：`max_steps` 限制一轮任务中的模型调用次数；`max_recent_turns` 限制保存多少轮完整对话，默认都是 6。

每次请求模型前，程序按下面顺序构造上下文：

```text
固定系统规则
→ 标注为背景资料的历史摘录
→ 最近完整轮次
→ 当前用户问题与本轮已经得到的工具结果
```

旧轮次会被压缩成摘录：用户输入前 400 字符、最终回答前 400 字符、最多三条工具结果各前 300 字符。完整轮次一起移除，避免工具结果留下了，却找不到原来的调用。

摘要本身也占空间。除了限制摘录原始长度，程序还检查整份内部 JSON 的实际字符数；引号和反斜杠转义会增加占用，不能只看原字符串有多长。全部完整历史清空后，仍需继续淘汰旧摘要，直到满足预算。若系统规则、工具定义和当前轮本身就放不下，则返回 `context_limit`，保留当前轮的完整配对，不强行截断发送。

这是一种简单、可解释的取舍：近期细节尽量保留，远期内容只留线索。它不能长期记住任意事实。比如预算限制写在长段落末尾，摘录可能漏掉；重要业务事实应另存为结构化记录。这也会在第 5 题中继续讨论。

## 7. 失败、保存和日志分别负责什么

工具参数错误会回传给模型，让它有机会纠正。HTTP 错误、超时、截断或无完整答案时，本轮会显示模型错误。达到步骤上限会标记未完成；这些都不会自动重新发一轮请求。

正常完成和可控失败都以一轮为单位保存。Ctrl-C 中断的当前轮不保存，之前完成的历史仍在。由于现有工具只读，这个选择适合本例；如果工具能下单，就必须在外部副作用发生前保存业务命令，不能套用相同恢复方式。

同一份会话可能被两个进程同时读取。SQLite 中的 `revision` 是保存版本：只有版本仍与读取时一致，更新才成功。竞争失败返回 `session_conflict`。这能避免覆盖别人已保存的对话，但两个进程在保存前仍可能都调用过工具。会话版本不是订单幂等机制。

`trace.jsonl` 一行记录一个事件，可用 `run_id` 串起模型开始、模型结束、工具结果和本轮结束。日志记录工具名、调用 ID、状态和耗时，不记录用户正文、工具参数或密钥。会话数据库则包含实际正文，两者用途不同。

```powershell
Get-Content -LiteralPath .local/walkthrough/demo/trace.jsonl -Tail 12
```

数据库打不开时，CLI 提示后以非零状态退出；`/sessions` 查询失败则提示并允许继续输入。不会为了恢复演示自动清空数据库。运行期间日志写入失败会提示并继续，启动阶段无法创建数据目录则属于启动失败。

## 8. 怎样判断实现真的通过了

各层测试直接覆盖实际工具、适配器和 Runtime；涉及模型时使用模拟模型或假 HTTP 传输，让异常可以稳定重现：

| 检查 | 它回答的问题 |
|---|---|
| 工具测试 | 参数类型、危险表达式、白名单和输出大小是否受到限制？ |
| Runtime 测试 | 工具结果是否正确回填？会话是否隔离？超限与保存冲突如何结束？ |
| 协议测试 | 请求和响应是否正确转换？进展、截断和不支持模式会不会误判？ |
| CLI 测试 | 空提问、数据库损坏或查询故障时，用户会看到什么？ |
| 组合测试 | 真实编解码器与 Runtime、SQLite、压缩组合后，协议状态是否保持完整？ |
| 干净包复现 | 新虚拟环境安装后，命令、切换和进程重启是否可用？ |
| 真实验收 | 当次远端配置下，模型是否完成普通追问、实际工具往返及会话恢复？ |

测试数量和最近结果统一见[验证说明](../verification/README.md)。版本冲突测试使用两份旧状态模拟竞争保存，不是多进程压力测试。真实验收会检查结构化工具结果，但其中三工具场景明确要求使用工具，不能据此推断任意含糊问题都能选对工具。

建议自己选三个测试，解释准备了什么输入、期望什么结果、删掉哪条保护会失败。能解释这些，比记住通过数量更有帮助。

## 9. 把实现和两道架构题联系起来

第 4 题继续问：如果 calculator 换成 create_order，超时后可以直接再执行吗？关键是让同一次业务操作有稳定身份，由业务服务去重，Runtime 根据工具策略决定能否重试。模型的工具调用 ID 只负责消息配对。

第 5 题继续问：对话里记着“待付款”，用户却已经在手机上付款，这时听谁的？订单服务负责当前业务事实；Agent 保留任务步骤和订单引用，需要当前状态时重新查询。现有 SQLite 保存会话，不能因为它也有一个 revision，就说已经实现订单一致性。

先读[第 4 题主答](architecture-q4.md)，再读[第 5 题补充](architecture-q5.md)。[详细讲解与答辩练习](architecture-defense.md)提供事务、幂等键、版本检查等解释，以及可以手动推演的故障。两题讨论的订单能力尚未加入当前代码。

实际讲解时，可以先演示计算与追问，再切换会话，然后解释压缩和测试证据，最后用下单例子说明写工具为什么需要额外设计。阅读和运行都只是准备过程；哪些部分已经理解，应由你自己动手解释和验证。

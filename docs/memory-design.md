# 记忆如何保存、召回和压缩

本实现的 memory 是会话内历史与有损摘录，不是跨会话个人画像，也没有向量检索。存储键是 `(user_id, session_id)`；两个窗口、两个用户分别读取自己的记录。SQLite 保存 JSON 形式的完整近轮次、历史摘录以及 revision。Responses适配时，assistant消息还携带经过校验的原生输出provider_items，包括phase、工具调用及供应商不透明加密上下文；随整轮一起保留、计入预算和淘汰，不解密也不写trace。更换供应商或模型时使用新数据目录，避免复用不兼容的加密状态。CLI 的 user 参数用于本地演示，不是线上鉴权。

## 一轮里面有什么

例如“算7+8”这一轮是：user 提问 → assistant 携带 calculator 调用 → tool 返回 15 → assistant 解释答案。若连续调用多个工具，所有调用和对应结果都属于这一轮。`tool_call_id` 配对工具请求与结果。

只在本轮完成、可控失败或达到上限时一次提交。模型失败后补充明确的失败回答，不假装任务成功。Ctrl-C 中断当前轮时不提交部分历史；已经完成的只读工具也不会改变外部业务状态。将来加入写工具，必须另行实现持久化执行记录与幂等，不能沿用“中断就不保存”来保证安全。

## 在什么时候召回，放在哪里

1. `Runtime.ask` 接到输入后，按会话键调用 `SessionStore.load`，得到当前独立状态。
2. 每次请求模型前，`MemoryPolicy.compact` 检查轮数和字符预算。
3. `MemoryPolicy.messages` 拼接：固定 system 规则 → 带来源声明的历史摘录 user 消息及简短 assistant 确认 → 最近完整轮次 → 当前尚未完成的一轮。
4. 工具结果以 tool 消息加入当前轮，下一次模型请求便能看到；用户下一轮追问也能看到已保存结果。
5. 本轮结束后再压缩一次并保存，下一次请求和重启后的请求都会读取到。

历史摘录放在 user 层级，工具结果保留 tool 层级；不把外部文本拼成新的高优先级系统指令。提示词说明其为背景数据，但这不能保证彻底消除模型的提示注入风险；本例额外通过三个只读工具和文档白名单限制能力。

## 两种上限解决不同问题

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `max_steps` | 6 | 当前用户请求最多调用模型6次，防止主循环无限继续 |
| `max_tools_per_step` | 4 | 每次模型响应最多4个工具调用；单轮最多24次执行 |
| `max_recent_turns` | 6 | 最多保留最近6个完整轮次，供后续追问 |
| `context_chars` | 18000 | 内部消息和 Schema JSON 的字符预算，超长时继续淘汰旧轮次 |
| `summary_chars` | 2400 | 摘录总字符上限 |

字符预算包含 system、当前轮、工具定义、历史和摘录，但不等于供应商转换后的精确 token 数。模型代码默认 `max_tokens=1200` 是响应预算，本次 6.1 真实验收显式使用 2400；不能用以上字符数推断真实计费。HTTP read timeout 也不是整次运行绝对截止时间。

## 压缩算法及丢失边界

超过轮数或字符预算时，从最旧完整轮次开始移除，提取用户输入前400字符、最终回答前400字符、最多3条工具结果各前300字符，标记 `lossy=true`。摘录区满后删除最早摘录，必要时截短单条。工具结果摘录是文字片段，可能不是完整 JSON；不会拿它重新执行工具。

摘录是放进消息里的 JSON 字符串，引号和反斜杠再次编码后会增加占用。因此，即使完整轮次已经全部移除，也要继续按实际 `size()` 淘汰最旧摘要，直到满足总预算。仅系统规则、工具定义和当前轮本身仍放不下时，Runtime 返回 `context_limit`，不截断工具配对后硬发请求。`compact()` 的返回值仍只统计移除的完整轮次，日志中的 `removed_turns` 不包含淘汰摘要的数量。

这能在短演示中保留先前约定、结果线索，不能保证长期保存任意事实。例如用户在很长消息末尾给出预算，截断后可能丢失。重要任务应在用户确认后转为结构化事实或业务记录；本题不扩展实现。

摘要不能恢复原文；本例也不保留被压缩轮次的无限原文归档。用户可以重新说明遗漏条件。测试验证摘要存在、旧信息召回到请求、结果片段被保留以及消息配对完整，不宣称“记忆保留率100%”。

## 并发、故障和存储边界

一个 Runtime 实例以锁集合拒绝同一会话同时运行；不同会话可以独立推进。不同进程通过 SQLite revision 的 compare-and-swap 保存：版本已变化就返回 `session_conflict`，防止静默覆盖。它不能阻止两个进程各自调用模型或执行只读工具，不是 exactly-once。

SQLite 的连接在事务完成后显式关闭，避免 Windows 文件占用。会话文件含用户原文和结果，未加密，默认放在忽略提交的 `.local/` 中；trace 不包含这些正文和参数。每个会话历史有界，但会话总数未做 TTL 或自动清理；演示之外要增加生命周期、备份、权限和总量控制。

# 关键 Prompt 记录

下面按任务整理。prompt 是意思还原，不是逐字聊天记录；当时的约束和取舍是实际用的。每条后面写了我怎么处理 AI 的输出，以及怎么验证。

## 1. 读原题，先列要求和不确定点

**当时想干什么**：先把题目要求抄准，不急着写代码。题目里有些要求很容易被顺手加码，所以先把范围钉住。

```text
你是后端面试官。下面是一份 Agent 方向的笔试题。只做两件事：
1. 把实作要求逐条列出来，不要补充题目没写的东西；
2. 标出你拿不准的地方，比如“思考过程”要不要展示、是否必须部署。
先不要写代码。
```

**它给了什么**：一份要求清单，外加几个它觉得模糊的点（思考过程、要不要 Web、要不要部署）。

**我怎么处理**：清单和我自己读的对了一遍，补了“最大轮次”“带工具的追问”“AI Prompt 记录”这几条；把“必须部署”划掉了，因为原题说 GitHub 链接即可。

**验证**：最后以 `docs/requirements.md` 为准，逐条对到文件和测试。

## 2. 设计最小主循环

**当时想干什么**：先把 loop 定下来，别一上来就做协议适配和压缩。

```text
我在写一个最小 Agent Runtime，不用 LangGraph 这类框架。先只给主循环的伪代码，要求：
- 输入用户消息；
- 模型可以直接回答，也可以返回一个或多个工具调用；
- 工具执行结果要按 tool_call_id 回填；
- 有最大模型调用次数，不能无限循环；
- 模型报错、响应截断、只返回进展说明时，不能当成功。
先不要写完整代码，也不要加 Web、数据库。
```

**它给了什么**：一个很短的 loop 骨架，基本就是“问模型 → 有工具就执行 → 再问”。

**我怎么处理**：骨架留下了，另外加了三层校验：模型返回格式、tool_call_id 不能重复、单步工具数上限。还把“模型只给进展说明”单独判成 `model_incomplete`，这个后来在 Responses 里用上了。

**验证**：直接回答、多工具、连续两次工具、达到步骤上限、模型报错，各写了一个测试。

## 3. 三个工具和 Schema

**当时想干什么**：工具能力可以小，但边界要硬。尤其是 calculator，不能给模型一个 `eval`。

```text
给我三个只读工具的设计，Python，标准库优先：
- calculator：不要 eval；只允许数字、括号、+ - * / // % **；限制长度、节点数、深度、数值和指数；除零、复数、非有限值要返回结构化错误。
- search：本地 JSON 语料，按关键词匹配标题和摘要，最多返回 3 条；明确标注是 mock，不联网。
- read_docs：只接受 runtime/session/memory 三个 ID，不接受路径。
每个工具给出名称、描述、JSON Schema、失败码。不要引入第三方搜索库。
```

**它给了什么**：三个函数的初稿，calculator 用了 `ast`，search 用了 `casefold` 和子串计数，read_docs 用 allowlist。

**我怎么处理**：留下思路，补了 Schema 的 `additionalProperties: false`、JSON 重复 key 拒绝、结果 JSON 往返、结果大小限制。search 的排序改成“先按分数，再按 document_id”，避免同分时顺序不稳定。

**验证**：`x+2`、`1/0`、`1e309`、`(-1)**0.5`、非法文档 ID、空 query、纯标点 query，都有用例。

## 4. 只读审查：让它找 bug，不要夸

**当时想干什么**：第一版跑通之后，我最担心的是“看起来对，但边界没处理”。所以让它只读审查，不许改文件。

```text
只读审查这个仓库，不要改文件。重点找会出问题的地方：
- 工具参数校验和异常路径；
- 模型输出不完整/被截断时会不会被当成成功；
- 会话并发保存会不会互相覆盖；
- 压缩后 tool_call 和 tool_result 会不会拆开；
- 日志里会不会出现正文、参数或密钥。
按严重程度排序，每条给文件、行为、复现方法。不要夸，也不要提“加前端/向量库”这种和题目无关的建议。
```

**它给了什么**：列了七八条，比较有价值的是 commentary-only、thinking 块、摘要转义后超预算、SQLite 故障处理。

**我怎么处理**：接受了前面几条；拒绝了“自动重试 HTTP”，因为超时不能证明远端没执行，这正好是第 4 题要讨论的；也没有加 Web/队列。

**验证**：每条修复都补了会先失败的测试，再跑全量。

## 5. 最小修复，不许重构

**当时想干什么**：审查之后容易手痒，想顺手重构。我给自己定了个规矩：只改确认的问题。

```text
只改上面确认的问题，不要重构。每个修复：
1. 先写一个会失败的测试；
2. 改最小范围；
3. 跑全量测试；
4. 说明这个修复的边界，尤其是它不能解决什么。
不要动 Responses 的 native replay 结构，除非测试证明必须动。
```

**它给了什么**：几次小 patch；有几次顺带改了结构，我把范围收回到已经确认的问题上。

**我怎么处理**：保留了“先写失败测试”的顺序；有两处测试夹具互相影响，改成独立 session 和独立 ID。

**验证**：64 项测试；干净目录复现；真实接口单独跑，不和离线测试混在一起。

## 6. 第 4 题：先要短答案，不要长文

**当时想干什么**：架构题最容易写成“什么都说了，但不知道重点”。所以先让它用 5 句话给核心，再展开。

```text
我在准备一道架构题：LLM 工具调用超时后重试，怎么避免重复下单，以及 Agent 框架怎么知道工具是幂等的。
先不要写长文。用 5 句话给核心方案，再列 3 个最容易被打穿的失败场景。
要求区分 tool_call_id、业务 operation_id、order_id；说明 UNKNOWN 时什么时候能同键重试、什么时候不能。
```

**它给了什么**：初稿基本是“用幂等键 + 唯一约束 + 查询”，方向对，但把 `tool_call_id` 和 `operation_id` 混在一起说了。

**我怎么处理**：把三个 ID 拆开；补了“同键异参冲突”“键过期”“外部服务没有查询接口”这几种情况；把“允许重试”和“确认成功”分开写。

**验证**：把失败矩阵逐条推演，看答案会不会自相矛盾。

## 7. 第 4 题：让 AI 扮演面试官挑漏洞

**当时想干什么**：自己写的东西容易越看越顺，找个“反方”来拆。

```text
你现在是面试官，负责挑这份第 4 题答案的漏洞。不要复述我的答案，只问问题：
- 哪些地方是“听起来对，但实现不了”？
- 哪些边界没覆盖：并发、超时、键过期、跨服务、多副作用？
- 哪些说法前后矛盾？
按“会被问倒的概率”排序，给 10 个问题，不要给答案。
```

**它给了什么**：10 个问题，比较扎的是“模型一次返回两个下单调用怎么办”“operation_id 谁生成、什么时候落库”“下游没有查询接口怎么办”。

**我怎么处理**：前两个补进了答案，第三个明确写成“查不到就保持待确认，不猜”。这次也说明架构答案不能只讲正常路径。

**验证**：对照原文逐条检查，确认前后表述不矛盾；有几条需要结合代码一起说明。

## 8. 第 5 题：用省心购的场景，不要泛泛谈“最终一致”

**当时想干什么**：第 5 题很容易写成“业务事实归后端、Agent 存任务状态”这种正确但空的话。想逼自己落到具体场景。

```text
第 5 题：Agent 和后端各存一份数据，怎么设计。
用下单/售后的场景，不要泛泛谈“最终一致”。分三类：业务事实、Agent 任务状态、对话记忆；说明谁写、谁裁决、恢复时查什么、版本冲突怎么处理。
先给 1 页以内的答案，再列 5 个追问。
```

**它给了什么**：三类状态的划分，以及“订单版本”和“会话 revision”不能混用的提醒。

**我怎么处理**：把“订单版本”和“会话 revision”单独拉出来讲；补了“后端成功但 Agent 没收到”“其他端已经付款”“后端暂时不可用”三个场景；明确写了任务恢复不依赖聊天摘要。原题提到省心购和光辰是同一家公司，如果要把例子落到具体业务，省心购的下单/售后是合适的场景。

**验证**：用同一个下单例子，把第 4 题和第 5 题的边界对齐，避免两题互相打架。

## 9. 提交前检查：不要加功能，只查缺项

**当时想干什么**：上传前最后一遍，怕漏提交项，也怕把本地东西带上去。

```text
按原题提交要求检查这个仓库：GitHub 链接、README（运行/系统设计/memory 召回与放置）、AI Prompt 与问题解决记录、真实 API 证据。
列出缺失项和多余项；不要建议加功能。特别注意：不要泄露 key，不要提交 .local/会话数据库。
```

**它给了什么**：一份缺项清单，提醒我 README 里要写清楚 memory 的召回时机，还有 `.local` 的排除规则。

**我怎么处理**：补了 memory 说明和运行步骤；把个人学习记录加进 `.gitignore`；确认没有 key、没有会话数据库、没有虚拟环境。

**验证**：重新跑 64 项离线测试；检查 Git 跟踪的文件数；确认 `HEAD` 和远端一致。

## 保留和没有采纳的几类建议

**保留下来的**：

- 先写会失败的测试，再修；
- 工具参数用 JSON Schema，拒绝未知字段；
- 会话保存用 revision CAS，而不是“最后写入者赢”；
- 第 4 题用“先查询、再按契约重试”的顺序；
- 第 5 题把任务状态和聊天记忆分开。

**没有采纳的**（理由主要是题目范围和证据成本，不是对错判断）：

- 加 FastAPI/前端/向量库——题目没要求，会让运行方式和证据变复杂；
- search 接真实网络——mock 更可复现，测试不受网络抖动影响；
- 用 Redis 做会话锁——单机 CLI 用不上，SQLite CAS 已经能说明并发边界；
- HTTP 自动重试——和“超时不等于未执行”冲突，这条后来成了第 4 题的核心；
- 打印 thinking 明文——可能包含敏感信息，也不是可靠的事实来源。

## 提交前复核后的收尾

复核时发现，早期 Runtime 会把失败提示也存成 assistant 消息；后来改成只有模型给出最终答案才保存本轮，并补了超时和步骤上限的回归检查。当前工具都是只读的，失败轮次里已经得到的工具结果也会丢弃；将来加入写操作时，需要另外做持久化执行记录和幂等恢复。

第 4 题主答在提交前压缩过一次，复杂故障推演仍放在详细讲解里。关于“思考过程”，项目只解析模型公开返回的文本、进展阶段和工具调用；不展示也不解密私有推理。只有进展说明时，程序会判为未完成，不会当作最终答案。

这里的 prompt 是按当时任务整理的内容，不是逐字聊天记录。后续想补的文档整理项放在工作记录里，属于说明完善，不代表实现或交付还有未解决项。提交前还用真实配置做了两次有界复核，首个请求都收到 HTTP 502；两次均无自动重试，脱敏证据放在 `verification`。这是当前接入服务的失败记录，不能和 10 月 9 日已通过的真实验收混为一谈。

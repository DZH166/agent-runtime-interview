# 第 5 题补充：Agent 与后端怎样管理数据

题意转述：传统业务数据由后端保存。业务流程越来越多地放到 Agent 后，容易出现 Agent 存一份、后端又存一份的情况，应该如何设计？

这里继续使用[第 4 题的下单例子](architecture-q4.md)。当前项目保存的是会话历史与摘要，没有实现下文的订单服务、任务执行表或事件通知。本文说明的是扩展设计，详细推演见[共用讲解稿](architecture-defense.md)。

我的做法是先明确每类数据由谁负责写入和裁决。订单服务决定订单是否创建、是否付款；Agent 保存任务进行到哪一步，以及涉及哪些业务记录。Agent 可以保存查询快照，但快照过期时应重新查询，不能拿它覆盖后端事实。

## 把三类状态分清楚

| 状态 | 谁负责 | 例子与保存方式 |
| --- | --- | --- |
| 业务事实 | 对应业务服务 | `order_100` 的商品、金额、支付状态和业务版本；由受控接口更新 |
| Agent 任务状态 | Agent 的执行管理模块 | 确认过的命令、`operation_id`、当前步骤、是否等待查单；独立持久化 |
| 对话记忆 | 会话模块 | 用户说过的话、工具结果摘录、摘要；可压缩和淘汰 |

“独立持久化任务状态”是指恢复任务所需的信息有明确的结构和保存时机，不依赖模型上下文能否记住。它可以和会话表部署在同一个数据库，但应有独立的数据模型。关键业务调用发出前就保存操作 ID 与命令，收到可信结果后再推进步骤。

订单快照可以包含 `order_id`、状态、`order_version` 和查询时间，供展示或推理参考。它是带来源和时点的观察结果。Agent 自己的“正在等下单结果”则是任务状态，两者可以暂时不同：后端已经成功，而 Agent 还在等待确认，是一种需要恢复的正常故障状态。

## 业务逻辑放到 Agent 后，后端仍负责什么

Agent 可以负责理解需求、选择商品、组织步骤、决定接下来查询或调用哪个工具。后端保留数据必须满足的约束，例如权限是否足够、库存能否扣减、订单当前状态是否允许修改，并在提交事务时检查。

这样无论操作来自 Agent、网页还是手机，都会经过同一个业务写入入口。判断“用户想做什么”可以由 Agent 承担；把一笔订单提交成什么状态，要由业务服务确定。Agent 的自由文本回答不能直接变成已付款或已发货的事实。

## 用四个场景说明一致性如何保持

### 1. 正常下单

用户确认购买一件商品后，Agent 先保存命令和 `operation_id = op_001`，任务进入等待执行结果的步骤。它通过工具调用后端，后端按第 4 题的幂等方式处理，在事务中创建 `order_100`，返回状态及 `order_version = 1`。

Agent 保存订单引用和这个观察到的版本，再把任务推进为已确认创建，向用户回复结果。它无须额外建立一套可独立修改的订单表；展示需要的快照可以从后端结果生成。

### 2. 后端已经成功，Agent 没收到结果

网络超时后，Agent 保留原命令和待确认步骤。恢复时按 `op_001` 查询操作结果，查到 `order_100` 就补上任务进度；结果仍未知时，遵守第 4 题的同键重试条件。

因此，后端订单提交与 Agent 任务更新不必强行组成一个跨库事务。前提是调用前的命令已经持久化，后端支持幂等和结果查询，恢复流程会继续检查待确认任务。只写一句“最终一致”而没有这些步骤，不能解决丢失响应的问题。

### 3. 用户在其他端更新了订单，Agent 的快照过期

假设 Agent 记着“待付款，版本 1”，用户随后在手机上付款，后端变成“已付款，版本 2”。当用户问当前状态时，Agent 应调用权威查询接口，而不是照着旧摘要回答。

修改已有订单时，还可提交自己观察到的 `expected_version`。后端在同一事务中检查业务版本和允许的状态变更；版本已变化则返回冲突，Agent 重新读取并评估操作。如果变化影响原先确认的业务条件，再向用户说明。即使刚查过状态，提交时仍要校验，因为查询和写入之间也可能发生变化。

这里的 `order_version` 和当前代码的会话 `revision` 含义不同。前者防止基于旧订单状态修改业务，后者只防止旧会话覆盖新会话；两者不能互相替代。缓存也不会自动获知其他客户端的更新，这类陈旧数据问题在常见缓存方案中同样存在。[Microsoft：Cache-Aside 的一致性限制](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside#problems-and-considerations)

### 4. 后端暂时不可用

Agent 可以告诉用户“上次查询时订单是待付款，当前暂时无法确认”，并标明查询时间。涉及修改的步骤保持待处理或待确认，不把本地猜测当成成功结果。

服务恢复后，再查询权威记录、检查版本和用户原意，决定继续还是结束。这个取舍会降低故障期间立即完成业务的能力，但不会为了给出流畅回答而制造第二套订单事实。

## 这套设计的边界

基础方案先采用业务接口、稳定操作 ID、任务记录和版本检查。只有当状态变化频繁、需要主动通知大量 Agent 时，再考虑事件推送；事件的重复、乱序和丢失恢复放在[共用讲解稿](architecture-defense.md)中讨论。

验证时应检查：聊天摘要被淘汰是否影响业务记录；后端成功而 Agent 重启后能否查回；其他端修改后旧版本写入是否被拒绝；后端不可用时是否错误宣称下单或付款成功。第 4 题保证同一次命令重试不会重复下单，第 5 题明确订单状态的来源及 Agent 如何恢复任务进度。
